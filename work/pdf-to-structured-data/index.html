Turning 30,000 PDFs into Structured Data

Backend / AI Engineer — RAG Pipelines, Batch Inference & Azure OpenAI

PythonRAGAzure OpenAIAzure BatchChromaDBasyncio

The Problem

A legal team needed to analyze tens of thousands of long technical PDF reports and extract a fixed set of structured answers per document — factual identifiers, technical conclusions, names, and evaluations.

Manual review did not scale: each document required answers to 16 predefined questions, and with 30,000+ files the total workload exceeded 480,000 extractions. Synchronous LLM calls (document × question) were not viable in time or cost. Runs lasted hours or days and needed resumption, partial results, and operational monitoring.

The goal was not a chatbot, but a production pipeline that turned PDFs into a structured CSV with high accuracy and fault tolerance.

Pipeline Architecture

I designed and implemented a producer–consumer system with three concurrent asyncio tasks communicating through queues — ingestion, inference preparation, and result monitoring all advance in parallel rather than in a single blocking thread.

Producer — groups PDFs into batches of 50, extracts text in parallel (PyMuPDF + ProcessPoolExecutor), chunks text (1,000 chars, 200 overlap), generates embeddings via Azure OpenAI, and stores them in an ephemeral ChromaDB index per batch.

Consumer — for each document and each of the 16 questions: semantic retrieval (top 100 chunks, filtered by document), CrossEncoder re-ranking (top 5), prompt assembly, and packaging into Azure Batch jobs (up to 10,000 requests per job). Each request carries a self-contained custom_id (document|question) so out-of-order results can be reconstructed.

Monitor/Writer — polls Azure Batch every 60s, downloads completed JSONL results, buffers rows, writes partial CSVs every 1,000 rows, and deletes the batch vectorstore only when all associated jobs finish.

Retrieval & Batch Inference

Vector search alone was fast but imprecise on specialized legal text. I implemented two-stage retrieval: embedding search over the ephemeral index, then CrossEncoder re-ranking to improve context quality sent to the LLM.

Instead of synchronous API calls across hundreds of thousands of inferences, I integrated Azure Batch API for async mass inference with a 24-hour completion window — the Consumer submits jobs and moves on without blocking the pipeline.

Ephemeral vectorstores per batch (~6k vectors each) replaced a monolithic index that would have reached ~1.8M vectors at scale — keeping memory constant, search fast, and failure scope limited to a single batch.

Resilience & Operations

Runs could last days, so I built recovery into the core design: on startup the orchestrator detects previous partial CSVs, skips already-processed documents, and resumes from where the run stopped.

Partial CSVs every 1,000 rows, webhook alerts every 30 minutes with progress, ETA, and disk usage, stuck-job detection after 6 hours, and emergency stop via config file.

When all tasks complete, an offline consolidation step merges partial CSVs into a single output — one row per document, one column per question.

Tech Stack

Python · asyncio · ChromaDB · Azure OpenAI · Azure Batch API · Sentence Transformers · PyMuPDF · LangChain · pandas · Docker

Impact

Production pipeline processing 30,000+ legal PDFs into a consolidated structured CSV — one row per document, one column per extraction question.

Made 480,000+ LLM extractions feasible through batch inference, parallel asyncio stages, and ephemeral indexing instead of a single monolithic vector store.

Fault-tolerant by design: resumable runs, partial outputs, operational monitoring, and automatic cleanup — suitable for multi-day batch jobs without silent data loss.
